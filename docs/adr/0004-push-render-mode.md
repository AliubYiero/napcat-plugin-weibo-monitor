# 0004 · 推送呈现双模式与长文补拉

## 状态

已采纳 (2026-10-22)

## 背景与问题

图片推送卡片是插件原有的交付形态，视觉信息完整，但依赖 Playwright 截图：浏览器不可用时整条推送只能降级，长文也会让卡片变得很高。另一方面，纯文本在截图不稳定、只关心文字或需要复制内容的场景更可靠。于是「推送呈现是否可配、两种模式各自负责什么」成为一个真实取舍。

同时，微博列表接口对长微博只返回截断正文，`isLongText` 为真时正文通常停在「展开 / 全文」之前。图片卡片与文本模式都需要完整正文，否则用户看到的内容是不完整的。

## 被放弃的方案与理由

- **只保留图片卡片**：截图失败时没有可控的文本交付形态，长文卡片高度也不可控。
- **只发纯文本**：丢掉卡片承载的头像、配图与转发块的视觉结构，不符合默认使用习惯。
- **按会话配置呈现方式**：同一博主向多个会话推送时，每个会话都要单独理解与维护模式；配置维度从「全局显示偏好」膨胀成「会话级渲染策略」。
- **图片模式同时发卡片和文本**：同一内容发两条消息，重复且增加打扰。
- **图片模式再追加原动态附图**：卡片内已经包含原动态图片，会重复发送。
- **在 `fetchMyMblog` 阶段全量补拉长文**：首绑播种、游标推进等场景并不需要完整正文，会为未推送的动态付出额外请求。
- **模拟点击「展开」再拦截响应**：展开按钮触发的就是同一个 `longtext` XHR；依赖页面 DOM 选择器更慢、更容易受微博改版影响，也违背「外部 API 统一走页面内 `fetch`」的既有决策。

## 结论

- 全局配置 `weiboPushRenderMode` 决定推送呈现方式：`image` (默认) / `text`。默认图片，保持既有行为；仅自建 WebUI 可见。
- 两种模式共用推送标题行、原文链接与附图顺序；图片模式使用整卡，文本模式使用固定文本模板与分割线。
- 文本模式的转发分割线上下各保留一个空行；原动态块依次展示原动态时间、昵称、链接与正文，原动态删除时只显示提示。
- 图片卡片渲染失败时回退文本正文，并补齐原动态附图；整条消息发送失败时再回退为不含任何图片段的纯文本。
- 长文补拉放在推送层、渲染之前：判定 `isLongText` (或正文含全文/展开链接) 后，按 `mblogid` 在微博页面内直接请求 `/ajax/statuses/longtext`，用 `longTextContent` 替换正文；主动态与原动态分别补拉。
- 长文补拉失败只记录日志并保留截断正文，不阻断推送，也不改变 Cookie 失效与风控退避的判定；补拉成功不额外持久化，避免把上游正文写入本地数据。
- 代价：每条长文动态多一次接口请求；`longtext` 接口结构变化时需要同步调整解析。
