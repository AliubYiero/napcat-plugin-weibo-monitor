# 0008 · 轮询对齐到本地墙钟刻度

## 状态

已采纳 (2026-10-22)

## 背景与问题

轮询一直是「上一轮结束后再等一个完整周期」的固定延迟: 02:06 启动, 后续就是 03:06、04:06……用户在配置里写的是「60 分钟」, 但状态页给出的下次时间总带着启动那一刻的相位; 5 分钟这类短间隔同样从一次随机启动时刻起算。用户真正期待的是「每小时整点」「每 5 分钟整分」这种可预测、可与其它任务对齐的节拍。

同时发现退避与固定延迟的耦合留有缺口: `nextDelay()` 取 `min(间隔, 剩余退避)`, 5 分钟间隔撞上 30 分钟风控退避时会每 5 分钟重试一次, 退避几乎失效。

## 被放弃的方案与理由

- **继续固定延迟, 只在界面上解释相位**: 不解决「下次时间取决于启动时刻」的根因, 轮询仍无法与运维窗口对齐。
- **用时间戳对间隔取模**: 实现最简, 但原点实际是 UTC: 间隔 1440 在 UTC+8 机器上会落在本地 08:00, 半小时时区连 60 的倍数都会偏。
- **让即时拉取推进网格相位**: 即时拉取算作「本刻度的轮次」, 下次时间就会取决于最近一次手动操作, `nextPollAt` 无法解释; 而 4 分钟内的第二轮拉取本来也拉不到新动态。
- **补跑错过的刻度**: 系统休眠或长轮转后会产生突发连发; 水位线机制本来就不要求「一个刻度不落」。
- **把整个循环交给工厂 (setTimeout + 重排都封装)**: 会把 `started` / `inFlight` / 停止检查与 `pluginState.timers` 注册一并搬进工厂, 与状态派生耦合; 只有「下一次延迟是多少」需要模式化。
- **退避继续走 `min(间隔, 剩余)`**: 短间隔下退避形同虚设, 与「退避期间别再打」的语义冲突。

## 结论

- 能整除 60 的整数分钟间隔 (1/2/3/4/5/6/10/12/15/20/30/60 及 60 的倍数) 走本地日历的刻度网格; 其余间隔 (7/45/90/100…) 保持从上一轮结束起算的固定延迟。
- 网格原点用本地日历分量, 不用 epoch 取模: 分钟网格落在本地整分, 小时/天网格落在本地零点 (1440 即本地 00:00)。
- 下一时刻取严格未来的最近刻度; 已错过的刻度全部跳过, 精确落在刻度上时取下一个刻度。
- 即时拉取 (启动、保存 Cookie、新增订阅、启用会话) 保留, 且不改变网格相位; 退避允许脱离网格, 等满剩余退避时间后重试一轮, 之后回到网格。
- 分发方式: 纯函数 `createPollSchedule(minutes)` 只在 `start()` 与配置变更时选出计划器 (网格 / 固定延迟) 并派生出 `nextDelay(now)`; tick 收尾只调用计划器, 轮询路径不再做模式判断。
- 非整数分钟在运行期四舍五入并钳到 1..1440, 状态上报归一后的值; 状态新增纯派生文案 `scheduleLabel` (60 → 每小时整点, 1440 → 每天 00:00, 其余按公式派生), 用于状态页与启动日志。
- 代价: 每次重排多做一次本地日历取整 (可忽略); 运行期改时区或夏令时切换会让已排定的那一轮偏差一次, 下一轮自动回到新时区网格; 非网格间隔仍会漂移, 需要文案说清; 对齐意味着整点可能与其它任务撞车, 失去固定延迟的天然错峰。
